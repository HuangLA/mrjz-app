# 开发规则

最后更新：2026-05-13

## 1. 架构边界

- 后端是赛事规则的唯一计算方。
- Web Admin 承载复杂写操作。
- 小程序和 H5 优先展示，不做复杂管理后台。
- H5 和小程序共用公开 API 和核心展示字段。
- `packages/shared` 只能放浏览器安全的类型、常量和格式化逻辑。

## 2. 赛事规则

- 普通小组赛、瑞士轮和淘汰赛都归属于 `tournament_stage`。
- 所有对阵最终落到 `series`。
- 单局 Dota 2 match 落到 `series_games` 并关联 OpenDota `match_id`。
- 积分榜、瑞士轮配对、淘汰赛晋级都由后端计算。
- 自动生成的赛程、配对和 bracket 都先进入草稿状态，管理员确认后才发布。
- OpenDota 结果和人工结果冲突时，不自动推进积分榜或 bracket。

## 3. 后端规则

- 所有外部 OpenDota 请求必须异步化、可重试、可记录。
- 所有管理员写操作必须写审计日志。
- 所有公开数据必须按赛季、赛事、联赛范围过滤。
- 个人数据只统计本平台赛事范围内的比赛。
- API 返回给前端的排名和 bracket 必须是后端已计算结果。

## 4. 前端规则

- 移动端信息密度参考当前 `docs/design/page-direction.html`，避免营销页式大标题。
- 比赛详情页允许长滚动，但模块要可降级。
- 管理后台优先列表、筛选、批量操作和异常处理效率。
- 不在页面里展示开发说明、键盘快捷键或实现细节。
- H5 必须保证手机浏览器无横向溢出。

## 5. 文档和进度

- 每个阶段开始前检查 `docs/PROGRESS.md`。
- 重要决策写入 `docs/PROGRESS.md` 的“决策记录”。
- 新增或改变业务规则时，同步更新 PRD、技术方案或专项规格。
- 如果实现与文档不同，优先修正文档或说明偏差原因。

## 6. Git 和提交

- 一个提交只做一个逻辑单元。
- 提交前至少运行 `git diff --check`。
- 修改静态设计稿时运行 `python3 -m html.parser docs/design/page-direction.html`。
- 不提交真实密钥、生产配置、构建产物、`node_modules`。
- 不回滚其他人或用户的未说明改动。

## 7. 测试策略

- 领域服务优先单元测试：TournamentService、排名计算、瑞士轮配对、bracket 推进。
- API 优先集成测试：登录、赛程 CRUD、赛果录入、OpenDota 同步状态。
- 前端优先页面冒烟测试：H5、小程序关键页面无空白、无横向溢出。
- 管理后台优先表单校验和权限测试。
